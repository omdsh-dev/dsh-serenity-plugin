owner 的直觉是对的：**三级不是"要发明的层级"，而是"宿主已经预留了表达它的两种机制，只是没有把它组织成第三级"。**

三条修正后的要点：
1. 🟢 **可表达**：宿主**显式保留**了一条给下游插件写自定义记录的通道（`ignorable` 标记 + `SessionEventMap` 声明合并），

## 2′. 🔴 **更正 v0.1 的错误结论**（必须显式留下）

**v0.1 写的**（错）：「插件无法把任何自己的概念写进宿主的会话模型……**硬障碍**」。
**错在哪**：我把"**读侧拒绝未知事件**"当成了终点，**没有读宿主对这条设计的完整说明**。
**宿主自己的原文**（`dsh-session/lib/types/known-event-types.d.ts:7-20`，**我已亲自逐字复核**）：

> "Downstream (out-of-repo) plugin events are outside this list by construction.
> **The persisted `SessionEvent.ignorable` marker is the compatibility mechanism; event-name registration was rejected**
> because it does not classify omission safety and would make reads composition-dependent."

⇒ 🔴 **这是有意的设计，不是遗漏**：宿主**故意拒绝"事件名注册"**（理由：注册只解决了"叫什么"，
没解决"丢了安不安全"，且会让读取行为依赖于装载了哪些插件），**改用「写入者自报安全标记」**。

**对 v0.1 那条"硬障碍"的准确重述**：
- ❌ 不是："插件不能写自定义事件"（**能写**，且是**契约内的机制**）；
- ✅ 而是："插件**必须自己声明**该事件是 `ignorable`（可安全跳过），**否则**读侧会拒绝整个会话"。
- **本容器 v1.29.1 撞墙的真实原因**：写 `serenity/bound` 时**没有带 `ignorable`** ⇒ 读侧拒绝。
  **而当时的代码根本表达不了它**——因为 `Session.append` 的信封只有 `{type,seq,time,data,surfaceOp?,sourceEventSeqs?}`。
  ⇒ **真正的障碍是"写入通道的表达力"，不是"词表封闭"。**

## 3. 🔴 那么"三级"到底卡在哪（**修正后的真问题**）

把 Q2 与 Q6 合起来看，**真正的缺口只有一处**：

> **宿主允许"往会话里加记录"，但（a）不允许"把关系写进会话的 header"，（b）不允许"注册一个新的分组层"。**
> ⇒ **三级不能靠"加字段"或"加类型"实现；只能靠"把轨迹表达成宿主已经认识的东西"。**

**这就把问题从"能不能扩展宿主"变成了**：
> **轨迹能不能被映射到宿主已有的两种机制之一**——
> ① **事件日志**（记录型：可记"这条会话属于轨迹 X"，但**读取方必须知道去哪读**）？还是
> ② **既有层级字段**（`parentSession` / `delegationDepth`：**宿主认识**，但**语义已被 fork/委派占用**）？

**这个映射才是本方向的真正设计题**（v0.1 完全没看到这一层）。三条可能的映射形态**待设计层展开**，
但**必须先由 owner 定 §4 的门**（D4），因为不同门后的可行解不同。

### 7.1 🔴 补齐后的关键发现：**插件可以自建"存储域"——但存储域 ≠ 层级**

**事实（`dsh-storage-domain/lib/types/index.d.ts`，已读）**：
- `ctx.storageDomain`（`DomainFacility`）**是公开面**：`open(spec)` / `get(name)` / `closeAll()`；
  导出 `defineDomain` / `domainTable` / `descriptorOf`（`index.d.ts:16`）。
- ⇒ **任何插件都能 `defineDomain` 自己的持久化域**（带 zod schema、版本、表）——**这是宿主明示的扩展面**。
- 先例：工作区自己就是这么做的（`dsh-workspace/lib/types/spec.d.ts:53-79`，`defineDomain({name:'workspace', version:2, tables:{workspaces: domainTable(...)}})`）。

**⇒ 对"三级"的准确意义（重要，且**不**翻盘 Q2）**：

| 能做 | 不能做 |
|---|---|
| 插件可以**自建一张表**，以轨迹为键存 `{轨迹 → 载体列表}`——**持久、有 schema、有版本、跨会话存活** | 🔴 **这仍然不是"层级"**：宿主**不认知**它。宿主的会话树（`deriveGroups`）、清理、`workspace.sessionIds` 都**不会**因为这个域的存在而改变 |
| 它能替代本容器现在的 `.bindings.json`，**并把它升级为宿主生态内的正规存储**（带 schema 校验、版本迁移、backend 路由） | 它**不能**让宿主 UI 把会话按轨迹分组，也**不能**让"会话属于哪条轨迹"成为宿主可查询的关系 |

⇒ 🔴 **这正好精确划定了 L2 的能力边界**：
> **L2 能做到"宿主生态内、有 schema 与版本的自建台账"（比 v0.1 判断的强），但做不到"宿主承认的层级"（与 Q2 一致）。**
> **"三级"的第二种分组关系，只有 L1 能真正提供。**

**顺带（与本令无关但值得记）**：`defineDomain` 是本容器**尚未使用**的宿主扩展面——
它是 `.bindings.json` / `wake-registry.json` 这类自建台账的**更正规替代**（有 zod 校验、版本、`per-record` 布局、`backup-and-skip` 策略）。
**建议登记为独立改进项**（不属本轮 §0C 结论，但成本低、收益明确）。

| 宿主**明确定义了会话事件的合法词表**：`KNOWN_SESSION_EVENT_TYPES` = "本仓库声明的每一个 `SessionEventMap` 成员"，并**明文写明**："**Downstream (out-of-repo) plugin events are outside this list by construction**" | `packages/core/session/src/known-event-types.ts:9-22` |
| 写入时**不校验**（"the unknown-type guard is deliberately **read-side only**"） | `coordinator.ts:772-776`；宿主设计注记 `2026-08-30-retain-ignorable-external-session-events.md:9-17` |
| 读取时**拒绝**：未知且非 `ignorable` 的事件 ⇒ **`SessionFormatUnsupportedError`**（整个会话**打不开**） | `packages/session/session-persistence/src/coordinator.ts:1248-1252`（调用点 `:1027,:1057,:1074,:1509`） |
| 而插件的**唯一写入通道** `Session.append(type,data)` **表达不了 `ignorable`**（envelope 只构造 `{type,seq,time,data,surfaceOp?,sourceEventSeqs?}`） | `packages/core/session/src/index.ts:668-698`；`types.ts:410,434-452` |

**本容器当年（v1.29.1）的实测后果**：dsp 曾**试图**把"载体↔轨迹绑定"作为自定义事件 `serenity/bound` 写进**会话日志**
⇒ **写入静默、读取爆炸**（含该事件的会话在冷加载时可能直接打不开）。
**处置**：v1.30.6 起**退出会话日志**，改存 CCC 内 `AGENT_SESSIONS/.bindings.json`（`trajectory-bound.ts:8-21` 有完整记载）。

### 2.1 这条障碍对"三级"意味着什么

🔴 **核心推论**：
> **插件无法把任何自己的概念写进宿主的会话模型**——**它能写事件，但不能定义事件类型；能读会话，但不能扩展会话的 schema**。
> ⇒ **"会话属于哪条轨迹"这个关系，今天在宿主侧无处安放**（既不能进日志，也不能进 header）。

**这直接决定**：三级**只有在下列之一成立时**才可能是"宿主承认的三级"：
- **(A)** 宿主提供**可注册事件类型**的机制（plugin → host 注册）；或
- **(B)** 宿主 `session.header` 有**可扩展的元数据字段**（自定义键）；或
- **(C)** 宿主提供**中间层的一等实体**（trajectory 本身）

……**若 (A)(B)(C) 全无** ⇒ 三级只能做"**半三级**"：**ACC 侧自建一层，宿主看不见**（详见 §4 的代价对比）。

> 宿主侧是否有 (A)/(B)/(C) 之一 —— **子代理取证中**（六个硬问题含"有无层级扩展缝"与"持久化面有无任意元数据字段"），回填本档 §2.2。

## 3. **一个关键的既有先例**：宿主自己已经在 session 之上挂了一层

§0C-3 已确证（回本仓编译期闸门 `src/host/type-contract.ts:131-134`）：

| 字段 | 含义 | 现状用途 |
|---|---|---|
| `header.origin` | `'subagent' \| undefined` | 标记派生会话 |
| `header.parentSession` | 父会话 | **会话之间已有父子关系** |
| `header.delegationDepth` | 委派深度 | **已有层级深度概念** |

⇒ 🔴 **含义（本调研最重要的正面证据）**：
> **"会话之上再挂一层关系"在宿主的类型系统里是被允许的**——这不是原理上不可行，**宿主自己就这么做了**（用于 subagent 委派）。
> 也就是说：**需要的不是"发明层级"，而是"让第三级获得与 subagent 委派同等的承认"**。

**这条同时降低了 §2 的悲观度**：既然宿主能表达 `parentSession`，那么"会话属于某轨迹"**在类型层面不是外来概念**——
**问题只在于**：这个关系能否由**插件**写（而非宿主自己写）。这正是 §2 的 (B) 那一格。

## 4. 三条路线的代价对照（**供 owner 挑，不预设结论**）

| 路线 | 形态 | 与 D4「零改 DSH」 | 能解 §0z-5 ② 的哪些 | 解不了哪些 | 代价 |
|---|---|---|---|---|---|
| **L1 · 宿主原生三级** | 宿主（或上游）把 trajectory 做成一等实体 | ❌ **破 D4**（须改宿主源码） | 几乎全部：实体、键、生命周期、UI、清理、轮换都能落到正确层级 | — | **须上游接受**（我们是下游插件）；升级耦合；D4 是本容器一贯约束，**破例须 owner 明示** |
| **L2 · 插件层"半三级"** | ACC 自建 registry（§0A-6 已设计），宿主看不见 | ✅ 守住 D4 | 键错位（§3.2 归位）、回收、轮换 | 🔴 **宿主侧仍以会话为单位**：会话列表 / `session-cleanup` / 宿主 UI **仍不认轨迹**（§0b 洞察三的盲区仍在） | 要长期维护一套"宿主不承认"的不变量（**正是 §0B 洞察一预言会反复复发的那种工作**） |
| **L3 · 中间态（本档倾向）** | **先做 L2 把 ACC 侧做实，同时向上游提"三级"的最小诉求**；等主编接受后再收敛到 L1 | ✅ 守住 D4（在"提诉求"阶段） | 先解 ACC 侧四条；为 L1 铺路 | 短期内宿主侧盲区仍在 | 两条并行；**须防止 L2 的临时结构固化成事实标准** |

**判据（选哪条，看一个问题）**：
> **宿主侧的那三个盲区（会话列表 / 清理 / UI）发生频率有多高？**
> - 高频 ⇒ **L1 值得破 D4**（或值得向上游正式提）；
> - 低频 ⇒ **L3**（L2 + 持续向上游提诉求）是性价比最高的。

## 5. §QX：必须核的一条（**owner 说"很多问题就解决了"——须逐条验，不能顺着说**）

owner 的直觉方向是对的，但"很多问题"要**逐条核**。按 §0z-5 ② / §0B 的清单逐项判定（**L1 假设**下）：

| 原问题 | 三级后是否真解 | 说明 |
|---|---|---|
| 词汇把主语指错（类 1） | ✅ **解** | 三级之后"轨迹"有了正式名字与位置，词汇自然归位 |
| `.bindings.json` 键错位 | ✅ **解** | 归属关系由宿主持有，不再需要旁挂表 |
| `pendingRebuilds` 载体键 + 仅内存 | ✅ **解** | 重建意图成为轨迹级（宿主持有生命周期） |
| `compactionStates` 键≠主语 | ✅ **解** | 同上 |
| keeper 两表无清理 | 🟡 **半解** | 若宿主提供轨迹级 disposal 事件则解；否则仍需自清 |
| `wake-registry` 只增 | 🟡 **半解** | **与本提议无直接关系**（它是 ACC 自建台账）；但三级后"轨迹级"的保留政策有了挂靠处 |
| 载体不可退役（无 `rotate`） | ✅ **解** | 三级之下"换载体"是自然操作（会话是轨迹的下级） |
| skiff 载体 id 是纯函数 | ✅ **解** | 同上——载体可换，轨迹不变 |
| §0b 洞察三（宿主共享盲区） | ✅ **解（仅 L1）** | **L2/L3 完全解不了这条** |
| §0b 洞察二（载体无法自证更替） | ✅ **解（仅 L1）** | 更替由上层权威确认 |

🔴 **诚实结论**：**在 L1 假设下，"很多问题"确实会解**（9 条里 7 条全解、2 条半解）。
**但 L2/L3 下只解 ACC 侧那几条，宿主侧盲区一条都解不了** —— 而恰恰是**宿主侧那几条**（清理不认轨迹、跨 CCC、列表以会话为单位）是当前最伤人的。
⇒ **这条把结论逼到一句**：**要真解，就得动到宿主层级本身（L1 或向上游推动）；只做 L2 是在重复 §0B 预言的复发循环。**
