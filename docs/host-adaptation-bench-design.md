## 一、为什么"运行态验收"必须外部化

三件事把本机封死了：

1. **本机宿主 = `0.1.5-rc.2`，而适配目标 = `0.1.7-rc.1`** ⇒ 适配后的插件**依赖新 API**。
2. **deploy 到旧宿主 = 当场打断本容器**（本会话所在的 runtime 就是它）⇒ 不能"就地试一下"。
3. **门禁是编译期/单测面** ⇒ 结构性地看不见"补丁层被静默跳过"这类运行期事实。

⇒ 结论：**运行态证据只能来自另一个宿主实例**。Docker（192.168.1.4）是这个"别处"的最廉价实现。

## 三、本台的边界（诚实声明）

1. 🔴 **没有模型凭据 ⇒ 真实轮次会以 `MISSING_CREDENTIAL` 结束** —— 但**这不影响 D3/V7b**：
   我们要测的缝（`bootstrap` / `agent/created` / `pre-step`）**都在模型调用之前执行**
   ⇒ **缝走到没有**已经确定；本轮实测：轮次记录完整（`turn/start`→`step/start`→…→`turn/end`），
   而失败点是 `MISSING_CREDENTIAL`（`model: deepseek-flash`）。**"轮次失败"与"缝没走到"必须分开报**。
2. **V5/V8 是"日志级 / 交付级"证据**，不是"用户在界面上看到了"；**真实浏览器级的界面证据仍未做**（登记为后续可选）。
3. **磁盘**：192.168.1.4 `/` 实测 **~19 GB 可用（97% 已用）** ⇒ 镜像精简、用完即清。
4. **`dsh plugin ... add` 的确切 flag** 以首次实跑为准；不符时**只改 `entrypoint.sh`**。
5. 🆕 **判据脚本是构建期 bake 进镜像的** ⇒ **改了判据必须先 `vpush`**（否则按旧判据验收 = 假红/假绿）；
   `V0` 就是为了把这件事**机械报出来**。

## 四、未来 rc 的复用姿势（**这就是"常驻"的含义**）

```
新 rc 出现
  → ① 拉源码/解包 + typecheck-host <新 rc>            （静态：B 面）
  → ② 对照新 rc 源码穷举契约面 A~C（🔴 **含 C6：运行时字符串成员表**）（静态）
  → ③ msm("bench-docker", ["build", "--dsh-version=<新 rc>"])   （本台；后台 + wait 收）
  → ④ msm("bench-docker", ["up", "--plugin-tarball"]) ＋ wait ＋ turn ＋ vpush ＋ verify
        （🔴 **顺序要点**：`turn` 造真实轮次 → `vpush` 推最新判据 → `verify` 读判据）
  → ⑤ 看 15 条判据是否全绿（**非绿先分诊：被测对象失败 vs 脚手架失败**）
  → ⑥ 全绿 ⇒ 走发布链（🔴 提交须排在 publish 之前，见 SESSION 判据 ㊱）
```

**每步的产物都是可复查的机械读数**，不依赖"我记得当时是这样"。
🔴 **本轮的两次自伤都出在"脚手架失败"上**（`--plugin-link` 无挂载通道 / `verify.sh` 是旧版）
⇒ ⑤ 的分诊**不是形式主义**：判据红了先问"**跑的是哪份脚本、走的哪条通道**"。
