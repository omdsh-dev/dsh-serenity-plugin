## 一、为什么"运行态验收"必须外部化

三件事把本机封死了：

1. **本机宿主 = `0.1.5-rc.2`，而适配目标 = `0.1.7-rc.1`** ⇒ 适配后的插件**依赖新 API**。
2. **deploy 到旧宿主 = 当场打断本容器**（本会话所在的 runtime 就是它）⇒ 不能"就地试一下"。
3. **门禁是编译期/单测面** ⇒ 结构性地看不见"补丁层被静默跳过"这类运行期事实。

⇒ 结论：**运行态证据只能来自另一个宿主实例**。Docker（192.168.1.4）是这个"别处"的最廉价实现。

## 三、本台的边界（诚实声明）

1. **无模型凭据 ⇒ 不跑真实对话轮**：验的是**装配面与插件面**，不是"一次完整对话"。
2. **V5/V6 是日志级证据**，不是"用户在界面上看到了"；要升到界面级需真实浏览器（**未做**，登记为后续可选）。
3. **磁盘**：192.168.1.4 `/` 实测 **21 GB 可用（96% 已用）** ⇒ 镜像精简、用完即清。
4. **`dsh plugin ... add` 的确切 flag** 以首次实跑为准；不符时**只改 `entrypoint.sh`**（装插件放在启动时而非构建时，就是为了这个）。

## 四、未来 rc 的复用姿势（**这就是"常驻"的含义**）

```
新 rc 出现
  → ① 拉源码/解包 + typecheck-host <新 rc>            （静态：B 面）
  → ② 对照新 rc 源码穷举契约面                          （静态：C 面）
  → ③ docker build --build-arg DSH_VERSION=<新 rc>      （本台）
  → ④ 容器内跑 verify.sh，看 V3/V4 是否绿               （运行态：D 面）
  → ⑤ 全绿 ⇒ 走发布链（🔴 提交须排在 publish 之前，见 SESSION 判据 ㊱）
```

**每步的产物都是可复查的机械读数**，不依赖"我记得当时是这样"。
