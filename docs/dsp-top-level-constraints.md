# dsp 顶层约束（Top-Level Constraints）

> **地位**：本文件是 `dsh-serenity-plugin`（dsp）的**顶层约束**——它规定"这个项目必须长成什么样、哪些事不能做"。
> **它下面的所有文档、代码、测试都必须服从本文件**；与它冲突的，以本文件为准（或先改本文件，再改代码）。
> **权威范围**：本仓（`AI_LAB/dsh-serenity-plugin`）的**架构、分层、衔接面、工程与测试纪律**。
> **维护规则**：改本文件 = 改项目的顶层规则 ⇒ 必须① 写明**理由与备选**（R↓）② 同批更新受影响的代码/测试/文档 ③ 记入本仓 `CHANGELOG.md`（若影响发布物）或本文件的「修订记录」。
> **立档**：2026-09-25，owner 令「我们要做一个能存活很多年的 plugin」＋ 六项工程化要求（见 §0.2）。

## 0. 定位

### 0.1 一句话

dsp 是 **DSH（DeepSeek Harness）运行时的 ACC 实现**：一个把"认知容器"装到宿主上的插件。
它由**独立仓**维护、以**npm 包**交付、被**多台机器/多个容器**安装。

⇒ 因此本项目最要紧的三件事，按优先级：

| 优先级 | 要什么 | 为什么 |
|---|---|---|
| 1 | **与 DSH 的衔接面可控** | 宿主在演进（rc 一个接一个），我们**零改宿主** ⇒ 宿主一变，我们只能在**自己的代码里**接住。衔接面是本项目唯一的结构性风险源 |
| 2 | **分层清晰、依赖单向** | 项目要活很多年 ⇒ 后来者（人或 agent）必须能在**不读完整个仓库**的前提下改对一处 |
| 3 | **可验收** | "我以为它好了"不是证据。每一条约束都要有**机械判据**，没有判据的约束只是愿望 |

### 0.2 这份文档服务于什么

它由一次六项工程化要求催生（owner 2026-09-25）：① 顶层约束文档（= **本文**）② 清死代码、整理代码 ③ 功能块列表 ＋ 抽象分层 ④ 按③做功能无影响的重构 ⑤ 成体系、抽象分层的单元测试 ⑥ 在容器基础设施上做集成测试体系（可安装／可启动／功能可用／用真实模型跑通）。

**进度与逐轮证据不写在本文件**（避免双真相源）：程序进度记在 CCC 维护会话 `S142` 的 `SESSION.md`；本文件只记**规则**。

## 1. 不变量（Invariants）

> **违反任一条 = 缺陷**（不是"风格问题"）。每条给出**判据**——没有判据的条目，等于没有约束。

| # | 不变量 | 判据（怎么机械地知道没违反） | 违反的后果 |
|---|---|---|---|
| **I1** | **零改宿主**：不修改、不 patch、不 fork DSH 的任何源码或安装副本；一切能力**经缝获取** | ① 仓内无对宿主源码的写路径（只有 `_tmp/host-*` 只读取证副本）② 所有宿主交互都出现在 `ctx.on(...)` / `ctx.<service>` 上 | 宿主升级即碎；且失去"可独立交付"的资格 |
| **I2** | **衔接面分级收敛**：① **禁止** import 宿主**内部实现路径**（只吃公开包入口与类型）② 禁止访问**未在 `inject` 或契约表声明**的服务 ③ 宿主类型的接触点**收敛到白名单**（见 §2.6） | ① `grep -rn "from '@deepseek-ai/\|from 'cordis'" src/` 的清单与 §2.6 白名单逐条比对 ② 契约表 (`HOST_SERVICES`) 与 `inject` 是"允许使用的服务"的唯一名单。🔴 **现状（2026-09-25 实测）= 146 处（含 2 行注释；真导入 144），尚未收敛**；**白名单 = 本文件 §2.6**，**逐文件收敛清单 = 本文件 §2.7**（🔵 单真相源：清单**不写在模块图**；模块图 §3-1 只留指针与一句话结论） | 宿主 API 变化会**散落全仓** ⇒ 适配成本随模块数增长（本项目最大的隐性成本）。🔴 **本条是"目标态 + 迁移路径"，不是已达成的事实** |
| **I3** | **配置归属二分（D23）**：**ACC 管机制与数据，CCC 管措辞与纪律**；判据 = **改它要不要发版** | ① 机制/开关/阈值/白名单 → 插件全局或 CCC 配置键 ② 面向人的**文字**（提示词措辞、对外文案）→ CCC 侧 ③ 逐条审计 ACC 内嵌文案（**未决项 A11**） | 把 CCC 的观点焊进发布物 ⇒ 一处措辞要动全部容器；或反之，机制散在 CCC ⇒ 无法升级 |
| **I4** | **对外面纯净**：`skiff-` / `acp-` / `rebuild-` 前缀的会话与 3081/3099/3100 三个面属**对外面**，不得泄漏本地维护内容（本地维护会话豁免） | 输出守卫（`src/output-guard*.ts`）装配证据 ＋ 外部面测试 | 家庭/外部可见面泄漏内部细节 |
| **I5** | **零运行时第三方依赖**：`dependencies` 为空，能力由宿主 peer 提供（`plugin-development-standard` F6） | 读 `hooks/dsh-serenity-hooks/package.json` 的 `dependencies` | 与宿主带的版本打架；供应链面变大 |
| **I6** | **失败必须可执行**：失败要么**响亮**（抛错/非零退出），要么**带可执行信息**；禁止"沉默地什么都不做" | ① 门禁项都有非零退出路径 ② 面向 LLM 的失败必须含**原因＋可用清单＋修法**（见 `src/handyman-ops.ts:providerAvailabilityError` 的形态） | "exit 0 但其实没生效"这类事故——**本项目已多次踩到** |
| **I7** | **声明—现实一致**：任何"文档/注释/回执说的事实"都必须能被一次取证复现；断言与事实不符视为缺陷 | 每条声明给**取证方式**（命令/文件/运行态读数）；无取证的声明**不许写进文档** | 文档腐烂 → 后来者按错的模型改代码 |

## 2. 与 DSH 的衔接面（本项目最脆弱处）

### 2.1 三个面，分别管什么

| 面 | 内容 | 谁负责 | 判据 |
|---|---|---|---|
| **类型面** | 我们引用的宿主类型/服务成员的形状 | `src/host/`（`contract.ts` / `type-contract.ts`） | 对**真宿主包**跑 `typecheck-host <version>`（替身不算） |
| **运行面** | 宿主实际注入了哪些服务、事件名是什么、缝在何时被调用 | `src/seams/` ＋ `src/index.ts` 的 `inject` | 容器集成台（`bench/`）＋ 运行期自证行 |
| **版本面** | 我们声明支持的宿主范围 | `package.json` 的 `peerDependencies` ＋ `REQUIRED_HOST_RANGE` | 契约检查（`hostContract` 读数）＋ `host-fetch` 对撞 |

### 2.2 契约文件是"单一真相源"

- 宿主服务与成员的表 **只写在 `src/host/contract.ts`**；类型面只写在 `src/host/type-contract.ts`。
- **其它任何文件不得复制这两份表**（复制 = 第二真相源 = 迟早不一致）。
- 新增一个宿主能力时：**先加进契约表 → 再加使用点**（顺序不能反；反了就是"用了没声明的服务"）。

### 2.3 宿主漂移的处置流程（**固定为五步，不许跳**）

1. **取真包**：`host-fetch <version>`（**逐包用 `@deepseek-ai/` 作用域名**；第三方如 `@deepseek-ai/cordis@<ver>` 读在场包的 `package.json` 定版本）
2. **静态对撞**：`typecheck-host <version>`（node ＋ client 两半都要绿）
3. **契约穷举**：新宿主源码里搜我们依赖的服务/事件/字段（`docs/host-adaptation-bench-design.md` §C）
4. **运行态验收**：容器集成台装**真 DSH ＋ 真插件**，跑判据（§5.4）
5. **落地**：提交 → 具名发布令 → 发布链（§4.2）

> 🔴 **漂移分两类，处置不同**：**接口漂移**（改名/搬家/字段变）⇒ 跟着改；**原理不可行**（机制被移除/语义反转）⇒ 必须改设计，**不许硬凑**。

### 2.4 衔接面的禁止事项（逐条都是踩过的）

1. ❌ 直接 `import` 宿主**内部实现路径**（只能吃它公开的包入口与类型）
2. ❌ 使用**未在 `inject` 声明**的服务（Cordis 会给出 undefined，而失败往往很晚才显形）
3. ❌ 把 **CCC 的概念**（skill 文本、会话目录、家庭语义）带进 `src/host/`
4. ❌ 依赖**事件名的巧合**：事件改名是静默的 ⇒ 每个依赖的事件都必须在契约表里有记载，且有运行期自证
5. ❌ 收窄 `peerDependencies` 范围来"解决"兼容问题（`bundle` 的版本不兼容是**静默**的：启动 `skip` ＋ 一行 stderr）
6. ❌ 用"替身 ＋ 静态审计"代替**真包**验证（替身漏掉过真实的类型层断裂）

### 2.5 客户端半的衔接（例外条款）

`src/client/` 跑在**浏览器**里，它引用的是**宿主客户端契约**（`configForms` / `slots` / RPC），**不能**被 `src/host/` 的 node 侧类型覆盖 ⇒ 它**豁免 I2 的字面 grep 判据**，但必须满足：① 客户端对宿主的接触点收敛在 `src/client/host-type-contract.ts` ＋ `index.ts` ② 由 `typecheck-host` 的 **client 半**把关（与 node 半分开跑）。

### 2.6 宿主接触点白名单（**分级**；I2 条款③ 的判据表）

> 🔴 **本节是本文件此前缺失的一节**：I2 条款③ 原文就写着「收敛到白名单（**见 §2.6**）」，而本文件当时**没有 §2.6**（§2.5 之后直接进 §3）⇒ **悬空引用**，2026-09-25 补齐。
> **白名单管的是"哪一层可以碰宿主的什么"，不是"列出文件名"** —— 列文件名会漂，判据不会。

| 级 | 形态 | 允许出现在 | 为什么 |
|---|---|---|---|
| **W1 · 必要接触** | ① `import type {} from '<宿主包>'`（**声明合并**）② `defineTool` / `ContentBlock`（**工具 API 面**）③ 宿主**运行时构造器**（`createUserMessage`／`deriveEventMessage`／`z`） | **L0**（`src/host/`）｜**L2**（`src/seams/`）｜**L3**（`src/tools/`）｜组装点 `src/index.ts` | ① 声明合并**天然逐包**（每个包的事件表各自合并），**无法中心化**；②③ 是"**要用的宿主能力本身**"，不是泄漏 |
| **W2 · 待收敛接触** ⚠️ | 直接 `import type { Context } from 'cordis'`，以及 `dsh-agent`／`dsh-session`／`dsh-llm` 的**类型** | **L1 一律不允许** | §3.2-3 硬规则：L1 出现宿主类型／`ctx`／事件名 ⇒ **记缺陷**。L1 出现即违反 I2 |
| **W3 · 禁止** | ① 宿主**内部实现路径**（`@deepseek-ai/<pkg>/(lib｜dist｜src｜internal｜esm｜cjs)/`）② 使用**未在 `inject`／契约表声明**的服务 ③ L4 客户端半触碰 **node 侧**宿主类型 | **任何层** | ① **实测 0 处**（2026-09-25）；②③ 分别由 `HOST_SERVICES` 契约表与 `typecheck-host` 把关 |
| **豁免** | L4 `src/client/` 对**宿主客户端契约**的接触 | **L4** | 见 §2.5 例外条款（豁免 I2 的**字面 grep 判据**，但由 client 半把关） |

**判据命令与它的已知盲区（引用读数前必读）**：

```bash
grep -rn "from '@deepseek-ai/\|from 'cordis'" src/            # ⇒ 146（含注释）
grep -rn "^import .*from '@deepseek-ai/\|^} from '@deepseek-ai/\|from 'cordis'" src/   # ⇒ 144（真导入）
```

🔴 **两个数都要报**：**146 与 144 的差 = 2 行"注释里的 import 文字"**（`src/client/index.ts`、`src/client/image-fallback-api.ts` 各一行，注释中引用了那句 import）⇒ **I2 的原命令会把注释算进去**。单报一个数就会与另一种量法互相打脸。

## 3. 抽象分层模型（规则）

> **本文件给层的定义与依赖规则；`docs/dsp-module-map.md` 给每个模块的落位。** 两者缺一不可，且**不许互相抄写**。

### 3.1 六层（按"离宿主多近"与"可测性"排序）

| 层 | 名字 | 职责 | 允许依赖 | 可测性 |
|---|---|---|---|---|
| **L0** | **宿主缝 `src/host/`** | 唯一能碰宿主包类型与服务的地方；把宿主能力翻译成**中立接口** | 宿主包（唯一允许的一层） | 类型面（真包对撞） |
| **L1** | **领域核心 `src/<domain>.ts`** | 纯逻辑与状态机：轨迹、唤醒、重建、CRO、时钟、绑定……**不知道宿主、不知道 UI、不知道工具** | L0 的中立接口（**注入**，不直接 import 宿主） | **单元测试主战场**（纯函数/纯状态机） |
| **L2** | **服务与适配** | 把 L1 能力接到具体载体：存储域、文件、HTTP、微信、ACP、Skiff…… | L0、L1 | 装配测试 ＋ 局部集成 |
| **L3** | **工具与面 `src/tools/` `src/faces`** | **薄壳**：参数校验 → 调 L1/L2 → 呈现结果；对外 HTTP/IM 面同理 | L0、L1、L2 | 契约测试 ＋ 端到端 |
| **L4** | **客户端半 `src/client/`** | 浏览器侧界面与 RPC 调用 | 宿主**客户端**契约（见 §2.5） | 客户端契约测试 ＋ 真浏览器 |
| **L5** | **开发面 `scripts/` `bench/`** | 工具链、测试台（**不进发布物**） | 任何层（含读源码） | 自测 ＋ 真机跑 |

### 3.2 依赖方向规则（**单向，不许环**）

```
L5 ──► (任意层，含读源码)
L4 ──► 宿主客户端契约
L3 ──► L2 ──► L1 ──► L0 ──► 宿主
```

**硬规则**：

1. **只许向下**（编号大的可以依赖编号小的所**暴露的中立接口**）；L0/L1 **不得** import L3/L4 的任何东西。
2. **不得成环**：发现环 ⇒ 记为缺陷，按 §6.1 拆分，**不许靠"反正能跑"放过**。
3. **L1 不得感知宿主**：L1 里出现宿主服务类型、`ctx`、事件名 ⇒ 违反 I2。
4. **L3 必须薄**：L3 里的业务逻辑行数应远少于它调用的 L1/L2。工具文件里出现状态机/持久化细节 ⇒ 应下沉。
5. **CCC 语义只允许出现在"读配置/读 CCC 文件"的边界处**（L2/L3），且必须经由显式路径参数，不许硬编码容器路径。

### 3.3 新模块放哪一层（准入三问）

1. 它碰宿主包类型或宿主服务吗？→ 是 ⇒ **L0**（否则违反 I2）
2. 它是不是"不依赖任何外部载体就能测"的纯逻辑？→ 是 ⇒ **L1**
3. 它是不是"把某个载体接上"或"给模型/用户一个入口"？→ 前者 **L2**，后者 **L3**；浏览器里的 ⇒ **L4**；只给开发者用 ⇒ **L5**

**同时**：新模块必须同批带上**它所在层要求的测试**（§5.2），且**必须出现在 `dsp-module-map.md`**。

## 4. 工程与发布约束

### 4.1 门禁（七项，交付前**全部自己重跑**，不引旧回执）

| # | 命令 | 判据 | 何时必跑 |
|---|---|---|---|
| 1 | `dsh-develop typecheck` | node ＋ client 两半都过 | 任何源码改动 |
| 2 | `dsh-develop typecheck-cli` | 根包（dev 工具）过 | 改了 `scripts/` |
| 3 | `dsh-develop typecheck-host <ver>` | **真宿主包**下 node ＋ client 都无类型错误，paths 全命中 | 任何碰衔接面的改动 ＋ 宿主升级轮 |
| 4 | `dsh-develop test` | 全绿（文件数/用例数**记录基线**，变化要能对账） | 任何改动 |
| 5 | `dsh-develop coverage` | exit 0（有覆盖率门） | 新增 `src` 模块（**必须同批带镜像测试**） |
| 6 | `dsh-develop build` | 双 bundle 产出（`lib/index.js` ＋ `lib/client.js`） | 发布前 ＋ 集成测试前 |
| 7 | `dsh-develop pack-check` | tarball 文件清单符合预期（含双 bundle） | 发布前 |

### 4.2 发布链（**顺序固定**）

```
bump（版本三处一致）→ 门禁七项 → CHANGELOG 条目 → 提交（显式路径）
→ publish → 落地判据（§4.3）→ 三推（origin / github / omdsh）→ tag（三推）→ deploy ＋ restart-web（若需）
```

🔴 **三条硬约束**：
1. **提交必须排在 `publish` 之前**——npm 的 `gitHead` = pack 那一刻的 `HEAD`；反了，`gitHead` 指不到发布内容。
2. **发布只在 owner 具名令下**（D14）。"继续吧""我都支持"是**方向授权**，不构成发布令。
3. **落地判据**：`npm publish` 的 **exit 0 不是证据**（见 §4.3）。

### 4.3 "发布成功"的判据（两条读数，缺一不可）

| 读数 | 判据 | 说明 |
|---|---|---|
| **权威记录** | `GET {packument}/{version}?write=true` == 200 | **普通 packument 走 CDN，可滞后 >10 分钟** ⇒ 判"有没有上去"必须用 `?write=true` |
| **包体可取** | `GET {dist.tarball}` == 200 | 这才是"用户能不能装" |

- 两条都 200 ⇒ 已落地。
- 记录 200 ＋ tarball 非 200 ⇒ **半上架**（npm `staged publishing` 待批准队列；同版本重发必 409，需**人工 2FA 批准**）。
- 记录非 200 ⇒ 根本没上去（看 npm 的实际输出，**发布命令的成功路径也不许吞输出**）。

### 4.4 版本面纪律

1. 宿主升级 = **一等事件**：`REQUIRED_HOST_RANGE` / `peerDependencies` 的范围**不得为"消掉告警"而收窄**。
2. 宿主预发布线（rc）**允许直接跑**，但"适配过"必须有**真包对撞 ＋ 容器运行态**两份证据。
3. `CHANGELOG.md` 是发布细节的**单一真相源**；会话记录只记裁决与状态。

## 5. 测试约束（分层）

### 5.1 五层测试模型（与 §3 的层一一对应）

| 层 | 测什么 | 手段 | 判据 |
|---|---|---|---|
| **T1 单元** | L1 的纯逻辑/状态机 | 直接 import，无宿主 | 分支覆盖；**不许靠替身掩盖逻辑** |
| **T2 契约** | L0 的类型面 ↔ 真宿主包 | `typecheck-host`（真包） | node ＋ client 双绿 |
| **T3 装配** | L2/L3 的**接线与语义**（缝在什么时候被调、参数对不对） | 替身 `ctx` 组装插件 | 既要有"接线钉"，**更要有语义断言**（"接线正确 ≠ 语义正确"） |
| **T4 集成** | 真实组合：真 DSH ＋ 真插件 ＋ **真实模型轮** | `bench/` 容器台 | 见 §5.4 |
| **T5 界面** | 浏览器里真的看得见 | 真浏览器（CDP） | 渲染证据 ＋ 截图 |

### 5.2 每层的"最小必须"

- **T1 是主战场**：L1 的每个状态机必须能被**不启动宿主**地测到（这反过来要求 L1 不依赖宿主 ⇒ 与 §3.2-3 互相成就）。
- **新增 `src` 模块 = 同批带 T1/T3**（本仓有 coverage 门，见 §4.1-5）。
- **碰衔接面 = 同批跑 T2**（真包）。
- **发布前 = T2 ＋ T4**（集成台）。
- **判据要有正控**：任何"防回归"的测试，必须能证明"撤掉修复就红"（否则它只是装饰）。

### 5.3 替身（fake/stub）规则

1. 只替**昂贵/非确定**的边界（LLM 适配器、网络、时钟、宿主服务）。
2. 替身**必须与真对象同形**（类型上能互换）——否则测试绿而生产红。
3. **不可替代真包**的场合：类型面对撞（T2）、真实安装/启动/对话（T4）。
4. 探针/夹具的**话术本身会改变被测对象的行为** ⇒ 设计替身与探针时必须自检"我有没有替被测对象做决定"。

### 5.4 集成测试体系（`bench/` 容器台）

**目标（owner 2026-09-25 令）**：**能安装 → 安装完成功启动 → 启动后所有功能可用 → 全程使用真实模型（MiniMax）**。

| 阶段 | 判据形态 | 现状 |
|---|---|---|
| **A 可安装** | 真 DSH ＋ 真插件装进 profile，无报错 | ✅ 已有（V1/V2/V2b） |
| **B 可启动** | 启动日志里补丁层**真的生效**（无 skip 痕迹 ＋ 我们的前缀在场），宿主版本正确 | ✅ 已有（V3/V3b/V4） |
| **C 功能可用** | 身份播种进会话 ／ 缝在运行期真被调用 ／ 设置面板装配与契约层正常 ／ 客户端 bundle 交付 | ✅ 已有（V5~V8） |
| **D 真实模型轮** | **用真实模型跑通一次完整用户轮**（回答正确、工具被调用、产物落地） | 🔴 **缺**（当前无模型凭据 ⇒ 只验装配面） |
| **E 界面级** | 真浏览器看到界面 | 🔴 缺（登记为可选） |

🔴 **本台的纪律（踩过的坑，不是风格）**：
1. **长任务一律后台脱离 ＋ 轮询**（远端命令先完全重定向再后台化），**绝不阻塞调用方**。
2. **`docker build` / `run` 绝不同步等待**。
3. **启动前先清结果文件**（否则上一轮产物让本次瞬间"判完成"）。
4. **改了判据要推进容器**（脚本是 bake 进镜像的，不然按旧判据验收 ⇒ 假红/假绿），且脚本要能**自证跑的是哪一份**。
5. **凭据不进镜像**：模型 key 只能通过**运行时注入**（环境变量/挂载的配置），不得 bake 进层里。

### 5.5 覆盖率与统计基线

- coverage 有门（exit 0 才算过）；**新增模块必须带测试**。
- **测试总数是基线读数**：数量变化必须能解释（例如"改了 N 个用例"）；对不上就查，不许含糊过去。

## 6. 演进与退役纪律

### 6.1 加东西（模块/机制/工具）

1. **先做 ontology 结构化**（领域实体/关系/约束）——本项目属于宁静号体系，遵循其 `home-ontology` 方法。
2. 定层（§3.3 三问）→ 写进 `dsp-module-map.md`。
3. 同批带**该层要求的测试**（§5.2）。
4. 碰衔接面的，同批跑 T2。

### 6.2 退役东西

1. 🔴 **先问"谁依赖它"**（grep：源码、测试、文档、脚本、CCC 侧 skill、其它仓）——**没有这一步的删除都是事故**。
2. 有活依赖 ⇒ **不能只删**：留**路牌**（说明对象已退场、替代品是什么），并让命令**非零退出**（`exit 0` 会让调用方以为"跑通了"）。
3. 证据要**双档**：① 源码面（导入/引用清零）② 运行面（不触发）。
4. 删除**必须**与它同批更新 `dsp-module-map.md` 与受影响的文档。

### 6.3 死代码的判定（可机械的部分与不可机械的部分）

| 判定 | 手段 | 注意 |
|---|---|---|
| **导出零引用** | 与 `tests/`、`scripts/`、`docs/` 分开统计：只被 tests 用 ≠ 活得健康，但**不等于可删** | 动态 import、字符串拼接的模块名、外部消费者（其它 CCC 的 CRO 程序）**grep 不到** |
| **运行期从未走到** | 集成台的运行期自证（缝/工具的调用痕迹） | 只有真实运行能回答 |
| **被替代但残留** | 对照 `CHANGELOG.md` 的退场记录逐条核 | 这是本项目**最常出现的**一类 |

🔴 **删除前必问三句**：① 谁依赖它（含仓外）② 它是不是"公开面"（工具名/包导出/HTTP 路由）③ 删了以后**失败会长什么样**（静默还是响亮）。
