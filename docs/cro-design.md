## §0 这东西用来干什么（白话，先说用途）

**今天：叫醒一条轨迹的方式是"几点几分叫我"。**

问题在于：**该不该醒，往往不是时间说了算。** 举三个真实的例子：

> · **S185**（管书房那台设备）应该「**天亮 + 家里有人 + 非高峰**」才醒 —— 现在是"每 2 小时"，天没亮也叫、没人在也叫；
> · 如果它**已经在干活了**，就不该再叫它一次；
> · 如果发现它**日志太大**（SESSION.md 快满了）或者**今天已经醒过太多次**，下次叫它时应该**要求它先整理自己**。

**⇒ CRO 就是干这个的**：让**一条轨迹自己带一段程序**，由 ACC 在每次检查时跑它，
**由这段程序决定"现在该不该叫我、叫我的时候说什么"**。

**一个类比**：今天像**闹钟**（到点就响）；CRO 像**一个值守的人**（看着情况，该叫才叫，叫的时候还说清楚要干什么）。

**它为什么重要**（owner 原话）：*"我们的 trajectory 唤起机制是**超长永续任务的基石**"* ——
现在的基石只认时间；CRO 让基石认**情况**。

## §1 归属与边界（**本节先立，后面全部由它推出**）

**所有者 2026-09-19 定**：

> **整个机制属于 ACC；CCC 是用户。**

| 面 | 归谁 | 含什么 |
|---|---|---|
| **机制** | 🔴 **ACC** | 契约（输入/输出）、调度（谁跑、多久跑）、执行（怎么起进程）、状态暴露（给什么数据）、容错（坏了怎么办）、**编写指南** |
| **程序** | 🔴 **CCC**（用户） | 那段判定的 **TS 代码本身** —— 放**轨迹自己的目录**里 |

**⇒ 一句话**：
> **机制在 ACC，程序在 CCC。** ACC **不碰任何一条轨迹的判定内容**；CCC **不定义任何机制**。

**这与既有机制同构**：`send-later` 是 **ACC 的工具**，用它在 **CCC** ——
CRO 是 **ACC 的机制**，写 CRO 程序的是 **CCC**。

**🔴 命名约定（防混淆，本节写死）**：
> **`CRO` = 那段程序**（实体名），**不是**"再发生"这个环节本身。
> 与 ACC 标准 §0.1 三环节（发生 / 存储 / **再发生**）的第三环**同源但不是同一个词**——
> 免得将来把"再发生"（理论环节）与"CRO"（实现机制）混为一谈。

**🔴 一处必须澄清的"看似矛盾"**：
- 所有者早先定过「**程序放轨迹自己的目录最合适**」；
- 所有者现在定「**整个机制属于 ACC**」。
- **两条不冲突**：**机制**（谁跑/怎么跑/给什么/吐什么/坏了怎么办）在 ACC；
  **程序**（判定逻辑）在 CCC 的轨迹目录。**边界干净。**

## §2 位置与形态

### §2.1 位置（唯一的，且在轨迹自己的目录里）

```
AGENT_SESSIONS/<轨迹目录>/continuous-re-occurrence.ts
```

**判据**：
- **文件名全写**（所有者令 2026-09-19）：`continuous-re-occurrence.ts`，不用缩写；
- **程序只有一个**（所有者令）：**文件在 = 启用；文件不在 = 禁用**。无 enabled 字段、无注册表、无开关文件；
- 放在**轨迹自己的目录**里 ⇒ ① 归属无歧义 ② **跟随轨迹跨载体存活**（rebuild 不换目录）
  ③ 天然进 git（CCC 是 git 管的）⇒ 可回溯、可重建。

### §2.2 语言与形态

**TS**（所有者令）。执行形态**沿用本容器已跑通的两处先例**：

| 先例 | 位置 | 已证明的能力 |
|---|---|---|
| `biasProvider` | `.opencode/skills/home-serenity/scripts/autopilot-round.ts:202-230` | `execFileSync` + **60s 超时** + `cwd=CCC_ROOT` + `SERENITY_CCC_ROOT` env + **多 runner 回退**（`process.execPath` → `bun` → `npx tsx`）+ **stdout 即内容** |
| `weixin.hook` | `src/weixin-hook.ts:152-190` | 同形态的**更严格版**：stdin 传 JSON + 超时 kill + 输出截断 + **旁路容忍**（失败绝不抛） |

⇒ **CRO 的执行 = 这两者的合体**：`biasProvider` 的多 runner 回退 + `weixin.hook` 的 stdin/stdout 契约与容忍。

### §2.3 🔴 运行契约 = B 案（**ACC 只 spawn，从不 import**）

**所有者 2026-09-19 定：B 是设计，A 只是文档友好；A 走 guide 老套路。**

| 案 | 形态 | 是否采纳 |
|---|---|---|
| **B · 进程边界** | ACC **spawn** 那个 TS 文件，**stdin 喂 JSON / stdout 收 JSON** | 🔴 **唯一运行契约** |
| **A · 文档友好** | 给一份"怎么写"的模板/骨架，让人好上手 | ✅ **采纳，但只作文档**（见 §8），**不进运行契约** |

🔴 **为什么必须是 B 而不是 A**：
若 ACC **import** 那段 TS（编译进来），就出现 ① **ACC 依赖 CCC 的源码路径**（npm 装机版在别处 ⇒
两条路径都要活 = 两个真相源）② CCC 的程序**语法错会让 ACC 启动失败** ⇒ **一个用户程序的错误放倒整个容器**。
⇒ **进程边界把这两件事同时挡掉**：**路径只需一个（文件系统），错误被隔离在子进程里**。

**所有者令 2026-09-19**：「**这个程序所得到的信息尽可能多，ACC/CCC 能拿到的都尽量给**」。

⇒ 形态 = **一个 JSON 快照**，ACC 每轮把它能看到的**全部**序列化后经 stdin 喂进去，**程序用不用随它**。

⚠️ **字段名以上为示意，最终以实现为准；本表的作用是"标出哪些是现成的、哪个是新增的"**。

### §3.2 🔴 唯一需要新增的内部能力：`runningTurns`（"是否正在跑轮次"）

**为什么它是唯一真新增**：§3.1 里其余各项**都是把已有的东西汇总一下**；
只有「**这条轨迹是否正在跑一轮**」**今天判不出来** ——
调度器只掌握**会话 live 与否**，而 **live ≠ 在跑**（一条会话可以 live 而空闲，本会话此刻就是活的反例）。

**⇒ 这是本设计里唯一需要 ACC 内部新增状态的地方，也是 §9 待裁项之一**。

**🔵 但本轮取证给出了一条好消息（降低该新增的难度）**：
宿主**已有两个插件可订阅的、且在契约表里的生命周期事件** ——
- **`agent/session-start`**（`host/contract.ts:275`，dsp 已在 `seams/context.ts:235` 订阅）
- **`agent/turn-stopping`**（`host/contract.ts:277`，dsp 已在 `rebuild.ts:442` / `output-guard-seam.ts:56` / `weixin-output-guard.ts:162` 订阅）

⇒ **"正在跑轮次"可以由这两个事件夹出来**：收到 `session-start`（或首个 turn 开始）⇒ 标记"在跑"；
收到 `turn-stopping` ⇒ 清除标记。**不需要新宿主能力，只需 ACC 自己维护一张小表**。

⚠️ **但那张表有两个必须一并设计的问题**（**这是 §9-1 的真正内容**）：
1. **清理**：载体被销毁 / 进程异常时不发 `turn-stopping` ⇒ **表会留下"永远在跑"的僵尸项**。
   ⇒ 须有清理判据（如"超过 N 分钟未收到 turn-stopping 即视为不在跑"）。
   🔴 **这正是本容器栽过 5 次的"只增不清"病的又一个候选点，必须在设计期就写清**，不得留到实现时。
2. **键**：这张表以**载体**为键还是**轨迹**为键？
   ⚠️ 若以载体为键，则**多载体轨迹**（S142 曾挂 4 条）要取"任一在跑"；若以轨迹为键，则须处理绑定变更。
   ⇒ 倾向**载体为键**（事件本来就以 agent/session 为主语）+ 查询时按轨迹聚合。

### §3.3 程序自己的记忆：**不在这里**（物理上给不了）

「它上次判了什么 / 连续几次说不该叫」这类**是程序自己的状态**，
ACC **拿不到也给不了**（那是另一个进程的内存）。

⇒ **归它自己**：程序可在**自己轨迹目录**里写状态文件（它自己读写）。
⇒ 🔴 **好处**：**"唤起计数"这类需要累计的量不必进 ACC** ⇒ **ACC 新增面更小**，
且**避免又造一个"只增不清"的表**（本容器栽过 5 次的那类病）。

## §4 输出：**是否唤起 + 唤起的提示词**

**所有者令 2026-09-19**：输出 = 是否唤起 + 唤起的提示词。

### §4.1 契约（stdout，JSON 单行）

```jsonc
{
  "wake": true,                    // 🔴 是否唤起（false / 缺省 = 不唤起）
  "prompt": "……",                 // 🔴 唤起时的提示词（wake=true 时必填）
  "reason": "……"                  // 可选：判定理由（进日志，供事后重建）
}
```

**三条边界裁定（供审核）**：

| # | 情形 | 处置 |
|---|---|---|
| 1 | `wake: false` | **什么都不做**（不投递、不记条目）——**这是常态** |
| 2 | `wake: true` 但 `prompt` 为空 | 🔴 **视为非法** ⇒ 记一行 + **跳过本轮**（不投递空消息） |
| 3 | `reason` | **可选但强烈建议** —— 见 §4.2 |

### §4.2 🔴 为什么 `reason` 很重要（CCE：重建 > 保存）

改成程序判定后，**"当时为什么叫了"不再能从时间表重建** —— 原因在程序肚子里（可能有随机、可能看了外部数据）。
⇒ **要求程序自报理由**，把"决策依据"重新变成**可重建的**（这是 CCE 的重建原则在机制层的落点）。
⇒ **与既有做法同源**：`biasProvider` 的输出本就是"给下一轮的文本"；`container_status` 等也都要求"可解释"。

### §4.3 "要求 trajectory 自整理"怎么表达

**不需要新机制** —— 它**就是 `prompt` 的一种内容**：

> 例：`"唤醒理由：SESSION.md 已 180 KB，请先压缩再继续。"`

⇒ 所有者举的第三个例子（"检测到 SESSION.md 过大则要求自整理"）**在输出面天然成立**，
**因为"要求"就是"唤起时说什么"**。**这也是为什么输出面只需要两个字段就够。**

## §5 容错

**所有者令 2026-09-19**：
1. 「**文件是半成品报错就好了，这么简单的事情，不需要想**」；
2. 同意容错设计（坏/超时 ⇒ 报错 + 跳过本轮）。

| # | 情形 | 处置 |
|---|---|---|
| 1 | **文件是半成品**（语法错 / 跑不起来） | ✅ **报错 + 记一行 + 跳过本轮**（所有者明示：不需要额外机制） |
| 2 | 超时 | 硬超时（沿用 60s 上限）⇒ kill + 记一行 + 跳过本轮 |
| 3 | 输出非 JSON / 垃圾 | 记一行 + 跳过本轮 |
| 4 | 输出非法（`wake:true` 无 `prompt`） | 见 §4.1 边界 2 |
| 5 | 进程起不来（runner 全失败） | 记一行 + 跳过本轮 |

🔴 **一条铁律（本容器的既有先例）**：
> **CRO 的任何失败，绝不影响既有机制** —— `send-later` / `send-now` / 唤醒表的投递**照常工作**。
> 先例 = `weixin.hook` 的**旁路容忍**（"失败仅日志返回，绝不抛，不阻断微信桥"）。

**⇒ 判据（可机械验）**：**把 CRO 写成故意报错的程序，跑一遍，既有投递链路必须一切正常。**

## §6 时序：与既有机制的关系

### §6.1 谁跑它、多久跑一次

**ACC 调度唤醒器**（`wake-scheduler.ts`，既有 **5min tick**）—— **所有者 2026-09-19 明示**。

### §6.2 🔴 与 `send-later` 的关系：**不是上下游，是两种唤起来源**

| | `send-later` | **CRO** |
|---|---|---|
| 何时说 | **人/agent 算好**一个时刻 | **程序按当时情况算** |
| 说什么 | **写死**一条 message | **程序按当时情况算** |
| 谁判 | 到点就投（无人判） | **一段非 LLM 程序持续判** |
| 生命周期 | **投一次即结案** | **持续存在**（文件在即生效） |

⇒ **两者并列，都终归落到"投一条 message 给某条轨迹"** ⇒ **投递面可复用，判定面是新的**。

### §6.3 与唤醒表（`wake-registry.json`）的关系

**CRO 不写唤醒表** —— 它是"**持续判定**"，不是"**某个未来时刻**"（表的语义专管后者）。
⇒ CRO 判定为真时，**直接走投递路径**（与 `send-now` 同面容），**不落表**。
🔴 **好处**：**不给 §0Q（投递即删、表只保在办）增加新的写入源**。

### §6.4 与 `v1.35.0`「ACC 侧 autopilot 退场」的关系（**澄清，防误读**）

⚠️ **不是走回头路**。v1.35.0 退掉的是 **ACC 的周期时钟 + 提示词生成**（判据 = 所有者「CCC 已能自己实现自己管理完整的 autopilot」）。
CRO 要的是**判据的执行器**：一段**非 LLM 程序**，必须有个**一直在跑的进程**去跑它 ——
**这正是 CCC 做不到的那件**（CCC 的自排是"被唤起时才跑"，**不能在没人醒着时判断该不该醒**）。

⇒ **ACC 提供"调度器 + 跑程序"是补位，不是回退**：退场删的是**判据内容**，不是**调度能力**（后者一直在，`send-later` 就是它）。
