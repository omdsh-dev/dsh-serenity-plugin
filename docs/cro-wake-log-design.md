## 0. 一句话（先说这东西解决什么麻烦）

**现在"ACC 到底叫过谁、叫了几次、哪次没叫成"，ACC 自己一个字都不留** —— 你想知道，只能去读**被叫的那个程序**自己写的记录；
**要是那个程序没写、写坏了、或者被换掉了，这段历史就是空白**。本方案让 **ACC 在自己那一侧留一份只记两天的流水账**，让"唤起历史"**不再依赖被观测者是否老实**。

## 3. 评估（为什么值得做）

### 3.1 缺口是真的：观测目前**全依赖被观测者的自我报告**

本轮（§7.14/§7.15）实测：我想知道"S185 昨夜被叫了几次" ⇒ **只能读它自己的 `cro-state.json`**；ACC 侧**零记录**。
⇒ 若程序没写状态、写坏了、或换实现，**"叫过没有 / 叫了几次"直接不可知**。
📌 与本轮两条判据教训**同族**：**"程序在跑" ≠ "程序在做判断"**、**"spawn 成功" ≠ "程序在说话"**；本条是第三次：**"程序记了" ≠ "ACC 记了"**。

### 3.2 owner 的洞察给出了正解方向

两条轨迹**自发**都做了结构化流水账（S151 `cro-state.json` + `recentWakes`；S185 同款）⇒ **"留痕"是真实需求**，不是我的偏好。

### 3.3 为什么**不是**第二真相源（铁律，必须写清）

**owner 把落点定在轨迹目录，恰好让这个分工在结构上一眼可见** —— 同一目录里并排两个文件，**主语各一**：

| 文件 | 谁写 | 主语 | 回答 |
|---|---|---|---|
| `<轨迹目录>/cro-state.json`（现存的，CCC 侧自由命名） | **CCC 的程序** | 程序 | 「**我判了什么**」（含"没叫"的判定、心跳阈值、环境谓词） |
| `<轨迹目录>/cro-wake-log.json`（**本方案新增**） | **ACC** | ACC | 「**我把什么送出去了、送成没有**」 |

⇒ **内容不重叠**：ACC 日志**不复制**判定细节；程序**不可能**知道投递结果（它是 fire-and-forget）。
⇒ **互补**：完整审计 = 两者合看（ACC = 投递面｜程序 = 判定面）。

## 4. 方案

### 4.1 落点与形态（**按 owner 07:2x 裁定**）

| 项 | 取值 | 理由 |
|---|---|---|
| **路径** | `<CCC 根>/AGENT_SESSIONS/<轨迹目录>/cro-wake-log.json` | **每轨迹一份**（owner 定）；与 CRO 程序、`SESSION.md`、程序状态**同目录** ⇒ **跟随轨迹跨载体存活**（与 §4.5.1 给程序选点的理由**同款**） |
| **文件名** | **`cro-wake-log.json`（固定）** —— 无日期、无版本、无轨迹名 | owner：「**文件名固定即可**」；**固定名 = 读取方无需猜**（与读侧"找 SESSION.md"同理） |
| **形态** | **`{ "version": 1, "entries": [ … ] }`** —— 与 `wake-registry.json` **同款结构** | 沿用本仓既有的 ACC 结构化状态形态（`version` 供将来演进；原子写 + 幂等清理的整套惯例可直接复用） |
| **写入** | **原子写（`tmp` + `renameSync`）**，与 `wake-registry.ts:118` 同款 | 半写不会毁档 |
| **何时创建** | **只在"该轨迹有 CRO 且发生了一次唤起尝试"时**创建/追加 | owner 原话「**当 cro 存在时**」⇒ 无 CRO 的轨迹**不产生任何文件**（零痕迹） |

> **备选（已否）**：① 每 CCC 一份单文件（v0.1 原方案）—— 与 owner 裁定不符；② 按日分文件 —— 与"**文件名固定**"要求冲突；③ JSONL 追加 —— 固定名下**仍须**按窗裁剪（见 §4.3），追加优势被抵消，且本仓 ACC 侧结构化状态已有 JSON 惯例。

### 4.2 每条字段（一次唤起尝试 = 一条 entry）

| 字段 | 内容 | 来源 |
|---|---|---|
| `at` | 时刻（**当地 RFC3339 带偏移**，沿 D67） | 调度器本刻 |
| `ok` | 投递是否成功（布尔） | **现成**：`deliverCroWake.ok` |
| `detail` | `已投递（live）` / `已投递（冷载入）` / 失败原因 | **现成**：`deliverCroWake.detail` |
| `tick` | 调度器 tick 计数（便于与 `acc-diag` ①b 对齐） | 本刻状态 |
| `reason` | 程序自报理由（**可为 `null`，但显式写出 `null`**，**不留空白** —— 同 §4.5.4 纪律） | 程序决策 |
| `promptDigest` | 唤起提示词**摘要**（长度 + 前 80 字） | **待裁**（§5-3） |

> `dirName` / `code` **不需存**：文件本身**就在该轨迹目录里**（位置即标识）——这是"每轨迹一份"带来的简化（少一处会漂的字段）。

### 4.3 轮转（owner 明示：程序化、2 日）

**写入时按窗裁剪 + 原子重写**（**单文件、固定名**下的唯一形态）：

1. 读现有 entries（读坏 ⇒ 当作空，**不抛**）；
2. 追加本次 entry；
3. **只保留 `at >= now - 2d` 的条目**（窗宽 = 常量 `CRO_LOG_RETENTION_MS = 2 * 24h`）；
4. 原子写回（`tmp` + `rename`）。

- **程序化**：窗宽是**常量**，**无配置键**、**无手动清理动作**；清理与写入**同一笔操作** ⇒ **结构上不存在"忘了清"的可能**（比"每 tick 跑一次清理"更硬）。
- 🔴 **写盘/裁剪失败绝不影响投递与既有链路**：整个记录动作 try/catch 包住，失败只进 tick 日志一行（与 §4.5.2「任何失败不得影响既有机制」同族）。
- 📌 **代价**：每次落盘重写整个文件。量级实测量 = **~36 行/天**（S185 40min 心跳）⇒ 两天窗 ≤ ~80 条、**< 20 KB** ⇒ **可忽略**。

## 5. 待裁点（白话 → 倾向 → 备选）

### 5-1 🔴 失败要不要也记一条？

- **白话**：真正的盲区不只"叫了几次"，还有**"该叫却没叫成"**（例如目标无 live 载体 ⇒ `acquireWakeAgent` 失败）——**今天这件事一个字不留**。
- **倾向**：**记**（`ok: false` + `detail` 带原因）。理由：**失败恰恰是最需要可见的那一半**；只记成功 = 留下"一切正常"的假象（与本容器反复栽的"安静失败"同族）。
- **备选**：严格照原话只记成功（更小更简单；代价 = 失败仍不可见）。
- ⚠️ 若采纳，文档/specs 里须把语义写成「**每次唤起尝试**」而非"成功唤醒日志"。

### 5-2 要不要纳入 git？

- **白话**：文件在轨迹目录里 ⇒ 默认**会**随 CCC 入库，且**每 40 分钟变一次**。
- **倾向**：**纳入**（体积小、随轮转自净、属可重建资产；换机器也看得到）。嫌噪音 ⇒ 给该文件名加 `.gitignore`（一处即可，不需动目录）。

### 5-3 唤起提示词存正文还是摘要？

- **白话**：提示词是程序写给人看的话，可能很长；全文属**程序产物**（它那边已有）。
- **倾向**：**摘要**（长度 + 前 80 字）——够定位、不搬第二份全文。

### 5-4 要不要同时写进标准（specs §4.5.5）？

- **白话**：specs 现写「要完整的逐次判定审计，须**程序自己**写状态文件」——加了 ACC 日志后这句**只对了一半**（判定面仍归程序，**投递面** ACC 自己有了）。
- **倾向**：**入标准**（做成**跨实现可对齐的可观测面**：文件位置 + 固定名 + 窗宽语义），否则另一个实现不做 ⇒ 同一 CCC 换个实现**可观测性就变了**（与 §5.12/§4.5 的入标准判据同源）。

### 5-5 `acc-diag` 要不要加一段显示最近若干条唤起？

- **倾向**：**先不加**（文件本身可读、名字自明；诊断段每加一段都有成本）。常用再加。

## 7. 成本与风险

| 项 | 估计（基于实测） |
|---|---|
| 写入频率 | 实测最高 = S185 **40min 一次**（≈36 条/天）；S151 ≈1 条/天 ⇒ 两天窗 **≤ ~80 条、< 20 KB** |
| 最坏情形 | 某程序"每 5min 都叫"（写坏了）⇒ 288 条/天 ⇒ 两天 **≤ ~600 条、< 100 KB**（仍小，且**轮转自带上限**） |
| 重写代价 | 每次重写整文件 ⇒ 最坏 100 KB ⇒ **可忽略** |
| **风险 1：只增不清** | 本容器**病族**（§0Q 前的唤醒表即此病）⇒ 本方案**从第一版就带轮转**，且**清理与写入同笔操作**（结构性防漏） |
| **风险 2：写日志失败连累投递** | 🔴 try/catch 隔离：**写日志失败不得变成投递失败** |
| **风险 3：被误当第二真相源** | 已在 §3.3 显式区分主语，且**结构上**表现为"同目录两个文件、两个主语" |
| **风险 4：污染轨迹目录** | 每轨迹只增**一个**固定名文件；无 CRO 的轨迹**零文件** |
