## 1. 用户模型（原话，R↓ 不可改写）

> "在设计上，skiff 应该区分的类型是临时和长期，临时的不绑定会话，skiff 提示词注入发生一次；长期的绑定 trajectory 也就是 SESSION.md，skiff 提示词每次用户消息都注入；发完当前版本再讨论吧"

解构为两个正交维度：

| 维度 | 临时 | 长期 |
|------|------|------|
| **会话绑定** | 不绑定（无 SESSION.md） | 绑定 trajectory（SESSION.md） |
| **提示词注入** | 一次（创建时） | 每次用户消息 |

## 2. 现状实证（v1.30.14 代码，全实证）

### 2.1 谁创建什么类型的 skiff agent

| 入口 | 代码位置 | sessionId | 现状类型 | 会话绑定 |
|------|---------|-----------|---------|---------|
| 微信桥 | `weixin-bridge.ts:229` | `skiff-weixin-<hash>`（按用户派生，稳定） | **长期** | ✓ 自动建/恢复（`ensureSkiffSession`） |
| ACP 3100 `session/new`（无 sessionId） | `acp-core.ts:153` | 随机 `skiff-<role>-<uuid>` | **临时** | ✗（`persistent=false` → 不建工作台） |

**判定方式 = 隐式**：`createSkiffAgent(..., sessionId?)` 的**是否传稳定 id**。无配置字段、无显式类型。

### 2.2 提示词注入现状（两个段）

| 段 | 内容 | 注册时机 | 文本求值 | 大小 |
|----|------|---------|---------|------|
| `serenity-skiff`（基础段） | `buildSkiffBasePrompt`（身份 + 白名单清单）+ **角色提示词全文**（`resolveRoleSystemPrompt`） | `createSkiffAgent` **一次** | **创建时快照**（闭包捕获字符串） | 角色文件大小（zhaocai.md = **18.2 KB**） |
| `serenity-skiff-workspace`（工作台段，v1.30.13） | `workspaceTrajectoryLine`（AUTO-BOUND + 路径 + 4 条纪律） | 长期型一次（幂等 WeakSet） | **动态**（每轮读 scope 的活跃 mdPath） | ~0.6 KB |

- **两者都进系统提示词**（每轮随 system prompt 重新发送，不是"只发一次"）
- **v1.30.13 起微信桥不再每轮往用户消息拼工作台纪律**（用户上一轮要求"不重复配置"）→ 现为单一注入点

### 2.3 由此产生的真实摩擦（本轮实证）

- **角色提示词是创建时快照**：本轮回改完 `zhaocai.md`（18.2 KB）后，**live 的招财 agent 仍用旧文本**——必须重启 dsh web（或重建该 agent）才生效。这是"提示词主权在 CCC 文件、生效权在进程"的错配。
- 临时型与长期型**当前注入行为完全相同**（都只在创建时注册段），差别仅在"是否建工作台"。

## 3. 目标 vs 手段（EAP：先把目标说清）

"每次用户消息都注入"是**手段**。它可能服务三个不同目标，成本差 10 倍以上：

| 目标 | 说明 | 每轮消息注入是否必需 |
|------|------|-------------------|
| **G1 热更新** | CCC 改 `zhaocai.md` → 立刻生效，无需重启 | ✗ 不必需——**动态系统提示词段**（`text()` 每轮重读文件）即可，零额外消息 token |
| **G2 在场保证** | 无论 agent 如何被创建/恢复，提示词必定在场 | ✗ 不必需——系统提示词段本身就是每轮在场（除非 agent 被别处重建且未挂段） |
| **G3 近因强化** | 提示词出现在**用户消息**里（recency 最强，紧贴本轮输入） | ✓ 必需——只有这一条要求走消息通道 |

## 4. 成本实证（决定方案取舍）

| 项 | 数值 |
|----|------|
| `zhaocai.md` | **18,196 B**（≈ 6k–9k tokens，中文） |
| 每轮注入角色提示词 | 每条微信消息 **+6k~9k tokens**（一天 50 条 ≈ **300k–450k tokens/天**） |
| 每轮注入工作台纪律块 | 每条 **+~200 tokens**（一天 50 条 ≈ 10k tokens/天） |
| 动态系统提示词段 | **0 额外消息 token**（系统提示词本就要发），但每次组装多一次文件读（缓存 mtime 可忽略） |

## 5. 候选方案

### 方案 A（推荐）——类型显式化 + 长期型提示词段动态重读
- 角色配置新增类型字段（如 `kind: 'temporary' | 'persistent'`，缺省由"是否传稳定 sessionId"推断 → 向后兼容）
- **长期型**：角色提示词段改为**动态**（`text()` 每次重读 `systemPromptFile`，mtime 缓存）→ **改文件即生效**（G1）；工作台段保持动态（G2）；不往用户消息注入（零额外 token）
- **临时型**：角色提示词段保持**创建时快照**（"注入一次"的字面语义）；不建工作台
- 达成：G1 ✓ G2 ✓ G3 ✗（成本最优）

### 方案 B（用户原述）——长期型每轮把提示词拼进用户消息
- 长期型：**移除**角色提示词的系统段，每轮 `question = 提示词 + 用户消息`
- 达成：G1 ✓（每轮重读文件）G2 ✓ G3 ✓，**代价 = 每消息 +6k~9k tokens**（一天 300k–450k）
- 备注：也可只注入"工作台纪律 + 关键纪律摘要"而非全文（折中 B′，每消息 +200~500 tokens）

### 方案 C（混合）——大而稳走系统段（动态），小而变走消息
- 长期型：角色提示词 → **动态系统提示词段**（G1/G2，零消息成本）；**工作台纪律 + 当轮状态**（SESSION 路径/绑定/未决项摘要）→ 每轮消息前缀（G3，小体积）
- 临时型：全部走系统段快照（一次）
- 达成：G1 ✓ G2 ✓ G3（对小而易变部分）✓，成本 +~300 tokens/消息

## 7. 兼容与迁移（实现时注意）

1. **存量 live agent**：改段逻辑不影响已注册段；重启后按新逻辑重建（微信桥 live 复用路径会重新挂段）
2. **`trajectory.session` 与 `kind` 的关系**：现状 `trajectory.session=true` 才建工作台——建议 `kind` 为**上位概念**，`kind=persistent` 时 `trajectory.session` 仍有独立开关权（能力 vs 身份）
3. **ACP/问答页**：对外面若允许传稳定 sessionId，就等于"长期型"——需明确是否允许（当前仅进程内复用）
4. **测试**：新增"临时/长期 × 注入通道"矩阵用例；沿用 v1.30.13 的 `ensureWorkspacePromptSection` 幂等测试
5. **文档**：`msm-ops` 的 CCC_CONFIG_REFERENCE（角色段）需补 `kind`；`weixin-doctor guide` / `.opencode/skiff/*.md` 同步
