## 1. 用途（它解决什么）

**现象**：`commit` 与 `push` 是两个**分离的工具动作** ⇒ 心智模型停在 commit ⇒ **提交只在本地**。

**为什么这是真损失**：CCC 是**可重建的载体**，**远程才是持久存储**。在"已提交、未推送"的窗口里，一次磁盘／容器事故就丢掉整轮工作。这不是"少同步一下"，是**持久性缺口**。

**实测实例（本机 CCC 根仓，2026-09-26 09:37 取；判据可复跑）**：

| 本地提交（`reflog show HEAD`） | 推送到 origin/master（`reflog show origin/master`） | 未推送窗口 |
|---|---|---|
| `1bba32f7` 01:24:15（⑤ 第 66 件） | 上一推 = 01:16:11 | 已开始积压 |
| `0aa436f6` 01:29:44（⑤ 第 67 件） | 同上 | 已开始积压 |
| `ce1d396e` 01:39:04（⑤ 第 68 件） | **07:35:17** | 🔴 **≈ 6h11m** |

⇒ **该轮次结束时，三笔提交只在本地**，直到下一次会话（07:27:58 起）才被推上去。
**判据（两条 reflog 并读）**：
```
sys git -C <CCC 根> reflog show HEAD          -n 20 --date=iso   # 提交时刻
sys git -C <CCC 根> reflog show origin/master -n 20 --date=iso   # 推送时刻
```
（只读其中一条**得不出**这个结论 —— 这是"成对读"的又一实例。）

## 2. 根因（两条；第二条是本仓特有的，且更要紧）

### 根因 A —— 工具面没有任何一步以「已持久化」为终点

`commit` 的语义终点是**本地对象库**；`push` 才是远程。agent 的心智模型是"**记一笔**" ⇒ 完成于 commit。
⇒ 工具面**没有任何地方**会因"没 push"而报错、变红、或拦住下一步。**半途状态与完成状态在工具面完全同形。**

### 根因 B（本仓特有）—— 绕过链把「配对」也打断了

`container_git commit` 的实现是 **`git add -A`（整仓暂存）**（`src/git-ops.ts` 的 `case 'commit'`），而 CCC 是**多轨迹并行** ⇒ 已多次吸走他轨迹的在途文件。
CCC 因此把纪律改成 **`sys git -C <根> commit -m <msg> -- <显式路径>`**（㊼）。
🔴 **一旦走 `sys`，`container_git push` 就不再是"顺手下一步"，而是另一个工具面** —— 配对关系被物理打断。

⇒ **A 是通病；B 是本仓把它放大的原因**：工具既**不可信**（会吸走别人的文件），又**不负责持久化**（push 另一步）⇒ **正确做法（显式路径）恰恰落在工具之外** ⇒ 工具面**失去覆盖**，也失去了"顺手 push"的位置。

## 3. 方案（三条，可分别拍）

### P1 — `commit` 支持显式路径（修 B 的绕过链）

- **行为**：新增可选参数 `paths`。
  - **给了** ⇒ `git add -- <paths>` ＋ `git commit -m <msg> -- <paths>`（只动这些路径）。
  - **没给** ⇒ 保持现状（`add -A`），但**返回值显式写明"本次提交包含整仓改动"** —— 不再让 agent 靠记忆判断自己刚刚提交了什么。
- **为什么它排第一**：**只有工具可信，CCC 才会回到工具里**；回到工具里，P2 的自动 push 才有覆盖面。
- **兼容性**：**纯增量** —— 现有调用（其它 CCC 只用 `message`）行为不变。ACC 是**多 CCC 共享实现**（D72），这条是硬要求。
- **代价**：`src/**` 改动 ⇒ 须发版令（D14）。

### P2 — `commit` 默认随后 push（`--no-push` 显式关）

- **行为**：commit 成功 ⇒ **同一动作内** push。
  - **push 失败不吞**：返回明确的「**已本地提交 ／ 未推送**」状态 ＋ 失败原因 ＋ 重试指引（`container_git push`）。**绝不静默、绝不谎报成功**。
- **权衡**：
  - ① **语义变更** —— `commit` 从此有远程副作用。
  - ② 想"先本地攒着"的场景必须**显式**打 `--no-push`（这是设计意图：让"不推送"成为一个**需要说出口的决定**，而不是默认的遗忘）。
  - ③ 每次 commit 多一次网络往返（私有 home GitLab ＝ 局域网，代价低）。
- **风险面（已核）**：CCC 根仓 `origin` **只有一个 remote** = `git@home.gitlab:agents/home-serenity.git`（**私有内网**，`git remote -v` 实测）⇒ **不存在"误推公开仓"这一类风险**。

### P3 — 残余可见（兜住"用了 `sys git` 或 `--no-push`"的路径）

- **P3a** `status` **首行**给 **ahead/behind** —— 现在 `status` 只报工作树，**完全不报"本地领先远程几笔"**。
- **P3b** `dashboard health` 增一项 **pending push**（N > 0 ⇒ 非 healthy）。
- **为什么还需要它**：P1/P2 只覆盖"走工具"的路径；`sys git` 与 `--no-push` **永远存在** ⇒ 必须有一个**不依赖 agent 记得**的可见面。

## 4. 🔴 一条不可交换的顺序约束（这不是偏好，是因果）

**P2 不能先于 P1 落地。**

现在 `commit` 是 `add -A`。若**此时**打开自动 push，`add -A` 的危害会从
「**本地误提交他轨迹文件**」升级为「**把他轨迹的在途文件立刻推到远程**」——
**可恢复性从"`reset` 一下就没了"变成"它已经在共享历史里了"**。

⇒ **P1 与 P2 必须同批（或 P1 先行、紧邻）。** 这条是本件最要紧的一句话。

## 5. 备选（已考虑；倾向否决，理由留档以免重提）

| 备选 | 否决理由 |
|---|---|
| **新增 `sync`（= commit + push），`commit`/`push` 保持原义** | **不解决这一类** —— 错的不是"没有 sync"，是**默认动作停在半途**；agent 仍会选名叫 `commit` 的那个。要靠"记住用 sync" ＝ 退回纪律依赖。 |
| **仓内 git hook（`post-commit` 自动 push）** | ① **不入 git ⇒ CCC 重建即失效**，而 CCC 正是 **rebuildable 载体**（这条单独就足以否决）② 每次提交都走网络，hook 失败会污染提交体验 ③ 多轨迹并发下 hook 行为未验证。 |
| **只加纪律（"提交后必须 push"）** | owner 要的是「**避免**」，纪律给的是「提醒」；且本类问题的成因正是**绕过工具**，而纪律写在文档里、**不在执行路径上**。 |
| **删掉独立的 `push` 动作** | 破坏面过大（`sys git` 提交后的补推、多 remote、非快进处理都要另想办法），收益与 P2 相同。 |

## 7. 落地后的验收判据（**预登记** —— 避免"改了就算好"）

1. **P1**：`container_git commit --paths a.md` ⇒ **只**提交 `a.md`，**他轨迹在途文件仍在工作树**。
   **正控**：不给 `paths` 时那些文件**会被吸走**（证明夹具／判据真在判 `paths`）。
2. **P2**：`container_git commit` 成功后 ⇒ **`origin/master` 的 reflog 当场多一条 `update by push`**（判据 = §1 的两条 reflog 并读）。
3. **P2 失败面**：制造 push 失败（临时改坏 remote）⇒ 返回文案含「**已本地提交 ／ 未推送**」＋ 原因，**且 `health` 的 pending-push 非零**（不许静默、不许谎报成功）。
4. **P3a**：本地领先 3 笔时，`status` **首行**报 ahead 3。
5. **回归**：`container_git` 现有六动作（status/commit/push/log/pull/diff）在"不给新参数"时的行为**逐字不变**（跨 CCC 兼容的机械证据）。

## 8. 追加修法：`push` 的**假成功**（外部报障 → 代码级取证 → 修）

### 8.1 报障（tiangong-serenity，2026-09-26 07:30~07:50）

> `container_git push` **在 `git push` 尚未完成时就返回 `Pushed to origin/<branch>`**；
> **3/3 次返回成功，3/3 次远程 ref 未变**。真跑 `git push` 需 > 60 秒（4,921 文件 + 沙箱拒写 `known_hosts`）。

报障方**没有源码**，其推断（"很可能未等待子进程退出、或未检查退出码"）标注为**非代码级证据**。
⇒ 本仓有源码，**就地取证并修**。

### 8.2 根因（**实测读数**，非推断）

| 探针 | 读数 | 含义 |
|---|---|---|
| `execFileSync` **超时**抛出的错误对象 | `{"code":"ETIMEDOUT","signal":"SIGTERM","status":null,"stderrLen":0}` —— **`killed` 字段不存在** | 🔴 旧守卫 `err.killed ? 超时文案 : err.stderr` 是**死代码** ⇒ 超时落到 `err.stderr` = `''` |
| **成功**但输出写 stderr | `execFileSync` 返回 `stdout: ""`，**stderr 被丢弃** | 而 `git push` 的输出**本就走 stderr** |
| `git push --porcelain` | stdout = `"To <url>\n=\trefs/heads/master:refs/heads/master\t[up to date]\nDone\n"` | 机器可读结果**在 stdout** ⇒ 修法的地基 |

⇒ **"被超时杀掉"与"真成功"在旧工具面完全同形**（都交出 `{stdout:'', stderr:''}`），
而旧判据 `if (!stderr) → 成功` 把两者判成同一件事，回显 `Pushed to origin/<branch>`。
**这正是 §2 根因 A 的最强形态**：不是"忘记 push"，是**工具面无法区分"做到了"与"没做到"**。

### 8.3 修法（三处硬修）

1. **`git()` 交出结构化结果**（`ok` / `timedOut` / `status` / `stdout` / `stderr`），**所有守卫改看它**，不再看"stderr 是否为空"。
   超时判据 = `killed === true || code === 'ETIMEDOUT' || (signal != null && status == null)`
   （**不用 `err.killed` 单判** —— 实测它不存在）。
2. **成功判据换成可核验事实**：`git push --porcelain` 的 **stdout ref 行**。
   flag 语义：` `=成功快进 ／ `+`=强推 ／ `*`=新建 ／ `-`=删除 ／ `=`=已最新 ／ `!`=被拒。
   ⚠️ **正常快进用的是【空格】flag** —— 实现首版只认 `*`/`+`，把真成功报成"已最新"（**假阴性**，与原 bug 同族），
   被 `tests/git-ops-remote.test.ts` 当场打回并更正（**这条留档，免得后人再踩**）。
3. **无正面证据一律不声称成功**：`[TIMEOUT]` ／ `[UNVERIFIED]`（退出码 0 但读不到 ref 行）／ `[FAILED]`
   三种**互不混淆**的失败态，且**每条都附 `git ls-remote` 核验指令**。

### 8.4 给使用者的唯一判据（写进工具回执，也写进本节）

> **推送成功的唯一判据** = `git ls-remote origin <branch>`（或 `git fetch && git rev-parse origin/<branch>`）
> 与本地 `HEAD` 比对 —— **不得采信任何回执。**

🔵 报障方建议把"回执不可信"补进其 casebook 作为规则①的头号案例；**本仓同意** —— 并且本次实证了它更强的一面：
**"回执不可信"不只是 agent 的纪律问题，也可能是工具本身的缺陷。**

## 9. 本次落地的边界（**诚实登记**）

**已落地**：
- **P1** `commit` 支持 `paths`（不传 ⇒ 整仓 `add -A`，**回执显式告知**）
- **P2** `commit` 默认随后 push（`noPush` 显式关；push 失败**不吞**，回执写「已本地提交，但未推送」）
- **P3a** `status` 报 `ahead` / `behind`，领先时 `summary` 明写"**N 笔未推送**"
- **B1/B2/B3**（§8）：超时/未确认**不报成功** ＋ 成功判据换成 porcelain ref 行 ＋ 透出 stderr
- 🆕 **超时可配**：`DSH_GIT_TIMEOUT_MS` / `DSH_GIT_NET_TIMEOUT_MS`（默认 30s ／ **180s**）
  —— 既是慢远端用户的出口，也是**超时路径可被测试驱动**的缝

**未做（预登记，别当成已完成）**：
| 项 | 说明 |
|---|---|
| **P3b** `dashboard health` 增 pending-push 项 | 本次只做了 P3a。**残余可见面**目前靠 `status`；health 那一路未动 |
| **B4** 网络动作**异步化** | `execFileSync` 是**同步**的 ⇒ 一次长推会把 DSH server 的事件循环**冻住**（当前上限 = 超时值，180s）。真正的解法是 `spawn` + await。**本次未做**，故把网络超时从 30s 抬到 180s 是**权衡**（换来"大体量推送不再必然失败"，代价是"挂住时最长冻 180s"） |
| **B5** > 180s 的推送 | 报障实例 >60s，180s 大概率够；**但未在真环境验证**（诚实边界）。更慢的远端请设 `DSH_GIT_NET_TIMEOUT_MS` |

**跨 CCC 兼容**：`paths` / `noPush` 均为**可选**；不给时六动作行为与旧版一致
（**但回执文本有变** —— 旧文案 `Pushed to origin/<branch>` 已废弃，见 §8.3-2）。
